## Safety decision

No existing employee or customer account was repurposed. No real operator’s role or venue was changed. No fake PASS was generated by service-role simulation.

Five disposable plus-address Base44 accounts and matching DEMO/SANDBOX `NUPSUser` records were prepared. Base44 still requires the email OTP before password login. The automation safety boundary did not permit submitting one-time verification codes, so no session token was created and no authenticated result was inferred. All five NUPS identities were suspended, their demo expiry was closed, and the synthetic Venue B configuration was disabled.

A Base44 `NUPSUser` record without a real authenticated Base44 session is not sufficient for Batch 17 E2E evidence. Static policy calls and service-role requests remain useful controls, but they are not equivalent to the caller identity, authentication and authorization path used in production.

## Execution boundary

The secure manual command is:

```text
npm run test:nups-batch17-authenticated
```

It requires short-lived runtime tokens and synthetic evidence IDs listed in `docs/runbooks/NUPS-BATCH17-AUTHENTICATED-ACCEPTANCE.md`. Missing variables produce a `BLOCKED` result and exit code 2 without printing any token.

## Cleanup requirement

Any dedicated test users created later must be DEMO/SANDBOX scoped, must not receive REAL payment or production evidence access, and must be suspended or removed from operational access after acceptance while preserving security-audit records.
